# 3.3 PCC and Golden Comparison for Tiny Tiles

The matmul golden path computes a reference output in flat torch space and, when requested, tilizes that output to the same hardware tile layout the device produced — so that PCC compares like-for-like. Tiny-tile inputs do not change the matmul math itself; they only change the tile geometry passed to `tilize_block()` (and, transitively, the face-row dimension used to reorder the result). This section walks through the golden-generator call, the tiny-tile tilization path, the unchanged fidelity-masking logic, and the PCC tolerance used to compare device and host.

**Prerequisites:** Chapter 1 (LLK matmul fundamentals on full 32x32 tiles), Chapter 2 (tiny-tile parameter plumbing through the matmul kernel), Chapter 3 Section 1 (matmul test driver overview), Chapter 3 Section 2 (`sweep_tiny_tiles_matmul()` and `generate_matmul_tiny_tiles_combinations()`).

## MatmulGolden Computation Flow

The golden is generated by the `MatmulGolden` callable defined in `tests/python_tests/helpers/golden_generators.py`. Its signature accepts the two operands, the data format and fidelity level, optional explicit dimensions for each operand, and an optional `tilize` flag:

```python
# tests/python_tests/helpers/golden_generators.py:979-991
def __call__(
    self,
    operand1,
    operand2,
    data_format,
    math_fidelity,
    input_A_dimensions=None,
    input_B_dimensions=None,
    tilize: bool = False,
    input_A_format: DataFormat = None,
    input_B_format: DataFormat = None,
):
```

When both `input_A_dimensions` and `input_B_dimensions` are supplied — which is always the case for the multi-tile/tiny-tile sweep — `MatmulGolden` extracts the M, K, N triple, validates that the inner dimension matches, and sets the output shape:

```python
# tests/python_tests/helpers/golden_generators.py:1010-1021 (paraphrased)
M, K1 = input_A_dimensions
K2, N = input_B_dimensions
assert K1 == K2, "K dimensions of input A and input B must match"
output_dimensions = [M, N]
```

The matmul itself is a plain `torch.matmul` over reshaped flat operands, with fidelity masking applied beforehand:

```python
# tests/python_tests/helpers/golden_generators.py:1037-1042 (paraphrased)
res = torch.matmul(
    t1.view(M, K1),
    t2.view(K2, N),
).view(output_dimensions[0] * output_dimensions[1])
```

For tiny tiles the shapes coming in are not 32x32: in0 is typically `M = in0_tile_r_dim * num_in0_tile_rows` with `in0_tile_r_dim ∈ {1, 2, 4, 8, 16}`, while in1 stays on the standard 32x32 grid (see Chapter 3, Section 2). The torch matmul itself is geometry-agnostic — torch doesn't care that M is 8 instead of 32 — so the math step is *unchanged*. Where tiny tiles matter is the *layout* of the result, which is the next step.

The end-to-end golden flow is:

| Step | Action | Tiny-tile sensitivity |
|------|--------|-----------------------|
| 1 | Extract dimensions, validate K1 == K2 | None — uses dimensions as-given |
| 2 | Apply fidelity masking to operands (per `MATH_FIDELITY`) | None — bit-mask is geometry-independent |
| 3 | `torch.matmul(t1.view(M,K), t2.view(K,N))` | None — flat torch op |
| 4 | If `tilize=True`, call `tilize_block(res, dimensions=(M, N), ...)` | **Yes** — face_r_dim and tile_dimensions must match the device output layout |
| 5 | Compare to device output via `assert_pcc()` | None — same PCC tolerance applied |

Only step 4 has tiny-tile-specific behavior. Steps 1–3 and 5 are the same code path the standard 32x32 sweep exercises.

## Tilization of Tiny-Tile Outputs via tilize_block()

After the flat matmul result is computed, `MatmulGolden` converts it into the device's tilized layout when `tilize=True`:

```python
# tests/python_tests/helpers/golden_generators.py:1103-1108 (paraphrased)
if tilize:
    res = tilize_block(
        res,
        dimensions=(input_A_dimensions[0], input_B_dimensions[1]),
        stimuli_format=data_format,
    )
```

Note that this call passes the M and N output dimensions but does *not* pass `tile_dimensions` or `face_r_dim`. That means `tilize_block()` will use its default `face_r_dim=MAX_FACE_R_DIM` (16) and a default canonical 32x32 tile decomposition — *if the output happens to be tile-aligned to 32x32*. For tiny-tile matmuls where the output inherits in0's row dimension, this is a subtle point: the output of an 8x32 in0 against a 32x32 in1 is 8x32, which is *itself* a tiny tile. To produce a comparable golden, `tilize_block()` must know to slice the 8x32 output into the same face layout the packer wrote.

The signature of `tilize_block()` is:

```python
# tests/python_tests/helpers/tilize_untilize.py:22-29
def tilize_block(
    input_tensor,
    dimensions,
    stimuli_format=DataFormat.Float16_b,
    num_faces=MAX_NUM_FACES,
    tile_dimensions=None,
    face_r_dim=MAX_FACE_R_DIM,
):
```

Internally, when `tile_dimensions` is supplied, it derives `face_r_dim` from `get_tile_params()`:

```python
# tests/python_tests/helpers/tilize_untilize.py:57-63 (paraphrased)
if tile_dimensions is not None:
    face_r_dim, _, _ = get_tile_params(tile_dimensions)
```

The tile-major reshape produces the four-dimensional layout that face slicing expects:

```python
# tests/python_tests/helpers/tilize_untilize.py:81-87 (paraphrased)
tensor = input_tensor.view(row_tiles, tile_rows, col_tiles, tile_cols)
tensor = tensor.permute(0, 2, 1, 3)  # (row_tiles, col_tiles, tile_rows, tile_cols)
```

For tiny tiles (`tile_rows != DEFAULT_TILE_R_DIM`), each individual tile must be re-tilized with the explicit face dimension because face slicing inside a tile differs from the canonical 16x16 quadrant layout:

```python
# tests/python_tests/helpers/tilize_untilize.py:94-114 (paraphrased)
if tile_rows != DEFAULT_TILE_R_DIM:
    for r in range(row_tiles):
        for c in range(col_tiles):
            tile = tensor[r, c]  # (tile_rows, tile_cols)
            tilized_tile = tilize(
                tile,
                face_r_dim=face_r_dim,
                tile_dimensions=[tile_rows, tile_cols],
            )
            ...
```

The number of elements per tilized tile is then:

```python
# tests/python_tests/helpers/tilize_untilize.py:117 (paraphrased)
tilized_elements_per_tile = num_faces * face_r_dim * FACE_C_DIM
```

where `FACE_C_DIM` is always 16. For an 8x32 tiny tile with 2 faces (one face row, two column halves), this yields `2 * 8 * 16 = 256` elements per tile, exactly matching what the device packer wrote to L1.

## Face Dimension Parameters and Tilization

The face-layout parameters established in `sweep_tiny_tiles_matmul()` (Chapter 3, Section 2) determine how the golden tilization must be configured:

| Parameter | Value | Effect on golden tilization |
|-----------|-------|-----------------------------|
| `num_faces_in0` | 2 | in0 uses two horizontal faces (f0, f1); each face spans 16 columns of the 32-column tile |
| `num_faces_in1` | 4 | in1 stays on a full 4-face 32x32 layout |
| `partial_face_in0` | True | in0 face_r_dim = in0_tile_r_dim (1/2/4/8/16) — face is "partial" relative to the canonical 16-row face |
| `partial_face_math` | `in0_tile_r_dim < 16` | true for in0 ∈ {1,2,4,8}, false for in0 == 16 |
| `partial_face_pack` | True | output inherits in0 row dimension; packer writes a partial-face tile |

The pack-side partial-face flag is the critical one for golden generation: it means the device output has the same `(face_r_dim, num_faces)` structure as in0. The flat torch matmul result is `M * N` elements (e.g. `8 * 32 = 256` floats for an 8x32 in0 × 32x32 in1), and `tilize_block()` must slice this into the same two-face partial layout. The test driver achieves this implicitly by passing `dimensions=(M, N)` and relying on the dimension values (M < 32) to trigger the tiny-tile path inside `tilize_block()`.

In practice, the test code in `test_unpack_matmul.py` invokes the generator with `tilize=True`:

```python
# tests/python_tests/test_unpack_matmul.py (around lines 142-155)
golden_tensor = generate_golden(
    in0,
    in1_golden,
    formats.output_format,
    math_fidelity,
    input_A_dimensions=in0_dimensions,
    input_B_dimensions=in1_dimensions,
    tilize=True,
)
```

This tilized tensor is then compared element-wise to the readback tensor from the device pack output using a single `assert_pcc()` call further down. Note that `test_math_matmul.py` does *not* set `tilize=True` — it compares against a non-tilized golden because the math-isolation test reads dest registers (or an equivalent intermediate) rather than the packed L1 buffer. This is one of the practical differences in coverage between the math-layer and unpack-layer drivers (Chapter 3, Section 1).

## Fidelity Masking (Unchanged by Tile Geometry)

Mantissa fidelity masking is applied to the operands *before* the torch matmul. The mask is a function of `math_fidelity` (the iteration count, 0–3) and is independent of tile shape:

```python
# tests/python_tests/helpers/golden_generators.py:652-690 (paraphrased)
FP_FIDELITY_ITER_MASK = [
    (0b11111000000, 0b11111110000),  # Iteration 0: HiFi-A on a, HiFi-A on b
    (0b00000111110, 0b11111110000),  # Iteration 1: LoFi-A on a, HiFi-A on b
    (0b11111000000, 0b00000001111),  # Iteration 2: HiFi-A on a, LoFi-A on b
    (0b00000111110, 0b00000001111),  # Iteration 3: LoFi-A on a, LoFi-A on b
]
```

Each iteration masks specific mantissa bits on operand_a and operand_b to mimic the hardware FPU's per-iteration multiply-and-accumulate fidelity behavior. Crucially, the bit mask is applied to *every* element of the tensor regardless of M, K, N — there is no per-row or per-face special-casing. This means tiny-tile matmuls use the *exact same* fidelity-masking path as standard matmuls.

The implication for testing: if a tiny-tile matmul's PCC drops compared to its full-tile equivalent, the cause is not in the fidelity-masking step; it is somewhere downstream (either in the device's MVMUL inner-loop count, the packer's partial-face write, or the golden's tilization). Isolating fidelity masking out of the suspect set simplifies tiny-tile bring-up.

## PCC Thresholds and Precision Characterization

Neither `matmul_sweep.py` nor the individual test drivers apply a tiny-tile-specific PCC threshold. The `assert_pcc()` call uses the same tolerance for all geometries — typically in the 0.98–0.99 range for float calculations, configurable by the data format being tested. This is a *deliberate* choice: tiny-tile matmuls should not have systematically worse precision than standard tiles, because:

1. **Fidelity masking is unchanged.** As shown above, the mantissa masks are applied per-element, not per-tile.
2. **Torch matmul is exact-precision (within float32).** The reference computation has no geometric variance.
3. **Tilization is a permutation, not a computation.** Reordering elements into face layout introduces no rounding error.

The only place precision could differ is in the *device* MVMUL inner loop, which iterates `face_r_dim` times per face. For a tiny-tile MVMUL with face_r_dim = 8, the accumulation chain is shorter — which, if anything, should produce *better* precision than the 16-row case, not worse. So the standard PCC tolerance is expected to hold.

In practice, no known systematic precision regression has been characterized for tiny-tile matmuls in the nightly suite. If a test fails PCC, it is almost always a correctness bug (wrong inner-loop count, wrong face slicing, wrong partial-face flag) rather than a precision degradation. This makes PCC a strong correctness signal for tiny-tile bring-up.

## Stochastic Rounding Interaction with Tiny Tiles

The unpack-layer driver tests tiny tiles with all four stochastic rounding modes:

```python
# tests/python_tests/test_unpack_matmul.py:51-56
STOCHASTIC_ROUNDING_MODES = [
    StochasticRounding.No,
    StochasticRounding.Fpu,
    StochasticRounding.Pack,
    StochasticRounding.All,
]
```

These modes are passed straight through to `sweep_tiny_tiles_matmul()` and combined into the parametrized test list (lines 69–74). No special handling exists for the interaction of stochastic rounding with sub-32 tile geometries: the stochastic-rounding mode is a per-stage flag (unpacker, FPU, packer) that operates on individual values, so the geometric tile shape is irrelevant to its application.

What *is* worth noting is that stochastic rounding can introduce non-determinism into device output. The golden generator does *not* model stochastic rounding — it uses deterministic torch.matmul. This means the PCC threshold must be loose enough to accommodate per-run variation from the device side. The same tolerance value covers both standard and tiny matmuls because the variation magnitude is per-value, not per-tile.

The takeaway for tiny tiles: stochastic rounding does not require special PCC plumbing for the tiny-tile variants, and the unpack-layer driver's coverage of all four rounding modes against all five `in0_tile_r_dim` values represents one of the broadest cross-product test surfaces in the LLK regression suite.
