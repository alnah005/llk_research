# 8.2 -- Failure Modes

This section catalogs nine failure modes in the Pi0.5 framework, ranging from resource leaks to data corruption. Each entry documents the trigger condition, the observable symptom, the root cause in the source code, and any existing mitigations.

---

## 8.2.1 Zombie Processes After Runner Crash

**Trigger:** The runner process (`pi05_pipeline_runner_device`) crashes or is killed with `SIGKILL` (which cannot be caught) while the device launcher child is running.

**Symptom:** The `pi05_device_launcher` process becomes orphaned. It continues running, holding the Tenstorrent device open and preventing subsequent runs from acquiring the device. Subsequent runs fail with "device busy" or "MeshDevice::create failed" errors. Running `ps aux | grep pi05_device_launcher` reveals the orphan.

**Root cause:** The child sets `PR_SET_PDEATHSIG` to `SIGTERM`:

```cpp
// pi05_pipeline_runner.cpp:639-640
if (pid_ == 0) {
    prctl(PR_SET_PDEATHSIG, SIGTERM);
```

This tells the kernel to deliver `SIGTERM` to the child when the parent process exits, regardless of how the parent exits (including `SIGKILL`). The device launcher handles `SIGTERM` by closing the MeshDevice and exiting cleanly.

**Residual risk:** `PR_SET_PDEATHSIG` has a known race condition on Linux: if the parent dies between `fork()` and `prctl()`, the child never receives the death signal. The window is typically a few microseconds. Additionally, `PR_SET_PDEATHSIG` is reset if the child calls `setuid()` after `prctl()` (security measure). The framework does not call `setuid()`, so this is not a concern.

**Existing mitigation:** The `run_hybrid.sh` script provides a second line of defense, killing stale processes before each run:

```bash
# examples/run_hybrid.sh:6-8
pkill -9 -f pi05_device_launcher 2>/dev/null || true
pkill -9 -f pi05_pipeline_runner_device 2>/dev/null || true
sleep 2
```

**Recommended additional mitigation:** The child should check `getppid() == 1` immediately after the `prctl` call to detect the race where the parent already exited. If the parent PID is 1 (init/systemd), the child should `_exit()` immediately.

## 8.2.2 /dev/shm Cleanup: Stale Descriptors Persist

**Trigger:** Any abnormal exit (crash, `SIGKILL`, power loss) leaves socket descriptor files in `/dev/shm/`.

**Symptom:** Two failure modes:

1. **Stale connect.** A new runner connects to a stale descriptor that points to an IOMMU mapping from a previous device context. Reads/writes through this mapping produce PCIe errors, device hangs, or silent data corruption.
2. **Hang.** The runner polls for descriptors that already exist from a previous run but point to a dead kernel, causing it to hang during "Waiting for socket descriptors."

**Root cause:** tt-metal's socket layer exports descriptors to `/dev/shm/` with predictable names:

```cpp
// pi05_pipeline_runner.cpp:697-702
descriptors.push_back("/dev/shm/tt_h2d_" + cfg.h2d_bulk_socket_id + ".bin");
descriptors.push_back("/dev/shm/tt_d2h_" + cfg.d2h_bulk_socket_id + ".bin");
```

The files are not cleaned up by the framework on exit. The socket-mode path uses `_exit(EXIT_SUCCESS)` (line 1196), which skips all destructors and atexit handlers, meaning even well-intentioned cleanup code would not run (see also [Section 8.2.6](#826-sentinel-duplication-two-sentinels-corrupt-next-run) for another consequence of `_exit()`, and [Section 8.4.1](04_operational_gotchas.md#841-devshm-socket-files-must-be-cleaned) for the operational fix). The `DeviceLauncher::stop()` destructor (lines 673-681) terminates the child process but does not delete descriptor files, because the descriptor filenames are generated by tt-metal's socket layer and not tracked by the framework.

**Existing mitigation:** `run_hybrid.sh` explicitly removes all stale descriptors before each run:

```bash
# examples/run_hybrid.sh:9
rm -f /dev/shm/tt_d2h_* /dev/shm/tt_h2d_* /dev/shm/tt_socket_manifest_* /dev/shm/pi05_*
```

**Residual risk:** If a user runs the runner binary directly (bypassing `run_hybrid.sh`), stale descriptors can cause silent connection to dead sockets. There is no automatic detection of stale descriptors and no `--clean` flag on the runner.

## 8.2.3 IOMMU Mapping Race: 2-Second Heuristic Sleep

**Trigger:** The host connects to device sockets before the device kernel has completed its IOMMU page-table setup.

**Symptom:** PCIe DMA transfers fail silently (data corruption) or loudly (IOMMU fault logged in `dmesg`, process crash). Depending on the IOMMU configuration, this results in:

- A PCIe completion timeout (device hang, requires reboot)
- A kernel `DMAR` fault logged to `dmesg`
- Silent data loss (write absorbed by IOMMU fault handler without notification)

**Root cause:** After the `DeviceLauncher` reports that descriptor files exist, there is no protocol to confirm that the device kernel has completed its internal initialization (IOMMU mapping, FIFO allocation, NOC address computation). The framework uses a heuristic sleep:

```cpp
// pi05_pipeline_runner.cpp:919-921
// Wait for device kernel init to avoid IOMMU mapping race.
std::this_thread::sleep_for(std::chrono::milliseconds(2000));
```

**Why 2 seconds:** This value was determined empirically. On the N150 with a single bulk socket pair, the device kernel typically completes initialization in 500-800 ms. The 2-second margin accounts for variability under system load. However:

1. **No detection.** If initialization takes longer than 2 seconds (e.g., due to system load, slow PCIe link negotiation, or kernel module loading), the race is not detected until the first H2D write fails.
2. **No retry.** There is no mechanism to detect that the first transfer failed due to the race and retry.
3. **Excessive for fast systems.** On a dedicated benchmark machine with warm caches, 2 seconds is wasted time multiplied by every run.

**Recommended mitigation:** Implement a handshake protocol where the device kernel writes a "ready" marker to a known D2H address, and the host polls for it with exponential backoff before proceeding.

## 8.2.4 PCIe Alignment Violations

**Trigger:** The `BULK_PAGE_SIZE` constant does not match the device kernel's `page_size` compile-time argument, or the staging buffer is not aligned to `BULK_PAGE_SIZE`.

**Symptom:** Corrupted data, PCIe transaction errors, or IOMMU faults.

**Root cause:** Both host and device must agree on the page size:

```cpp
// pi05_pipeline_runner.cpp:200
static constexpr uint32_t BULK_PAGE_SIZE = 4096;

// pi05_bulk_passthrough.cpp:37
constexpr uint32_t page_size = get_compile_time_arg_val(2);
```

The host sends `num_pages` pages of `BULK_PAGE_SIZE` bytes each:

```cpp
// pi05_pipeline_runner.cpp:517
uint32_t num_pages = (total + BULK_PAGE_SIZE - 1) / BULK_PAGE_SIZE;
```

If the device kernel was compiled with a different `page_size` (e.g., 2048 or 8192), the device reads the wrong number of bytes per page, misinterpreting headers and payloads. Specifically:

- The NOC write in the kernel (`noc_wwrite_with_state`) may cross a page boundary, causing a partial write that corrupts the D2H FIFO.
- The host-side `socket_->write()` may transfer the wrong number of pages, leaving partial data in the H2D FIFO.
- DEVICE_PULL mode's `noc_read_page_chunked` (kernel line 76-80) computes the PCIe source address as an offset from the FIFO base; a page size mismatch makes this arithmetic wrong, reading from incorrect PCIe BAR offsets.

Additionally, the `staging_` vector used by `BulkH2DChannel::send()` is allocated via `std::vector<uint8_t>`, which may not be page-aligned. While PCIe DMA typically requires only cache-line alignment (64 bytes), tt-metal's `H2DSocket::write()` may impose stricter alignment requirements depending on the IOMMU configuration.

**Existing mitigation:** The `BULK_PAGE_SIZE` is hardcoded identically in both files (4096). The page size is a compile-time constant in the kernel (passed via `compile_args`) and a runtime constant in the host (set via `set_page_size`). There is no runtime validation that both sides agree. A defensive improvement would be to include the page size in the H2D header and have the kernel validate it on first receipt.

## 8.2.5 TT_VISIBLE_DEVICES Interaction: Topology Discovery Crash

**Trigger:** `TT_VISIBLE_DEVICES` is not set, or is set to a device index that does not exist, on a system with multiple Tenstorrent devices.

**Symptom:** Topology discovery crash during tt-metal initialization. The device launcher exits immediately with:

```
MeshDevice::create failed with out_of_range: ...
```

Or a segfault in `tt::tt_metal::distributed::multihost::DistributedContext::create()` or the PCIe device enumeration code.

**Root cause:** tt-metal's `MetalContext` / `ControlPlane` performs topology discovery at startup, enumerating all Tenstorrent devices visible via PCIe. On a system with multiple N150 devices where some are physically disconnected (no ethernet mesh between them), the topology discovery code attempts to form a mesh and crashes with an `out_of_range` exception.

This is caught in the launcher:

```cpp
// pi05_device_launcher.cpp:121-128
try {
    mesh_device = bulk_only
        ? MeshDevice::create_unit_mesh(0)
        : MeshDevice::create(MeshDeviceConfig{MeshShape{1, 1}});
} catch (const std::out_of_range& e) {
    std::cerr << "\nMeshDevice::create failed with out_of_range: " << e.what() << std::endl;
    throw;
}
```

**Existing mitigation:** Two-layer defense:

1. The launcher sets `TT_VISIBLE_DEVICES=0` in bulk-only mode if not already set (lines 86-89).
2. The runner's fork/exec path also sets it in the child environment (lines 644-646).

```cpp
// pi05_pipeline_runner.cpp:644-646
if (!getenv("TT_VISIBLE_DEVICES")) {
    setenv("TT_VISIBLE_DEVICES", "0", 1);
}
```

**Interaction hazard:** The `run_hybrid.sh` script sets `TT_VISIBLE_DEVICES` for the **parent** process with a default of `1` (second device), not `0`:

```bash
# examples/run_hybrid.sh:12
TT_VISIBLE_DEVICES="${TT_VISIBLE_DEVICES:-1}" \
```

If the operator's machine has only one N150 (device 0), the script will select a nonexistent device. The child process's fallback to `0` only applies in `bulk_only` mode when the variable is not inherited.

**Residual risk:** If the user sets `TT_VISIBLE_DEVICES` to a device index that is itself disconnected, the crash still occurs. The framework does not validate that the specified device is reachable before attempting `MeshDevice::create`.

## 8.2.6 Sentinel Duplication: Two Sentinels Corrupt Next Run

**Trigger:** The host sends two sentinel messages to the H2D bulk channel (e.g., due to a retry after timeout, or a bug in shutdown logic).

**Symptom:** The device kernel processes the first sentinel, echoes it via D2H, and exits. The second sentinel remains in the H2D FIFO. On the next run (if the device is not reset), the new device kernel reads the stale sentinel as its first message and immediately exits, producing a confusing "Device launcher process exited prematurely" error with no indication that a stale sentinel was the cause.

**Root cause:** The shutdown sequence sends exactly one sentinel:

```cpp
// pi05_pipeline_runner.cpp:1132-1133
bulk_h2d->send_sentinel();
bulk_h2d->barrier();
```

The sentinel is a single page with `slot_id == 0xFFFFFFFF`:

```cpp
// pi05_pipeline_runner.cpp:547-551
void send_sentinel() {
    std::vector<uint8_t> page(BULK_PAGE_SIZE, 0);
    BulkH2DHeader sentinel{SENTINEL_SLOT_ID, 0};
    std::memcpy(page.data(), &sentinel, sizeof(sentinel));
    socket_->write(page.data(), 1);
}
```

The device kernel checks for the sentinel and breaks out of its main loop:

```cpp
// pi05_bulk_passthrough.cpp:92
if (slot_id == SENTINEL_SLOT_ID) {
    // ... echo sentinel, break
}
```

**Existing mitigation:** The framework calls `send_sentinel()` exactly once, and the `barrier()` call ensures the write completes before proceeding. The `_exit()` call at line 1196 prevents any destructor from sending a second sentinel (see also [Section 8.2.2](#822-devshm-cleanup-stale-descriptors-persist) for the stale-descriptor consequence of `_exit()`). However, there is no FIFO drain on startup -- the kernel does not flush stale data before entering the main loop. A production kernel should drain the H2D FIFO (reading and discarding pages until empty) before entering the work loop.

**Residual risk:** The `/dev/shm` cleanup in `run_hybrid.sh` removes descriptor files but does not drain FIFO contents. If a sentinel page remains in device memory across runs, the next kernel will exit immediately.

## 8.2.7 FIFO Size Underrun: Payload Exceeds fifo_size

**Trigger:** The padded H2D payload exceeds the configured `fifo_size`.

**Symptom:** The `H2DSocket::write()` call either blocks indefinitely (deadlock) or writes past the FIFO boundary (corruption).

**Root cause:** The framework validates FIFO sizing at startup:

```cpp
// pi05_pipeline_runner.cpp:848-854
uint32_t max_payload = sizeof(BulkH2DHeader) + pipeline_config.pixel.total_bytes();
uint32_t max_padded = ((max_payload + BULK_PAGE_SIZE - 1) / BULK_PAGE_SIZE) * BULK_PAGE_SIZE;
if (max_padded > pipeline_config.socket.fifo_size) {
    throw std::runtime_error("Padded H2D payload (" + std::to_string(max_padded) +
        " bytes) exceeds FIFO size (" + std::to_string(pipeline_config.socket.fifo_size) + ")");
}
```

This catches single-transfer overflow. However, the check does **not** account for the scenario where multiple users' payloads are in-flight simultaneously. For the default config:

$$\text{max\_padded} = \lceil \frac{8 + 451584 + 4096}{4096} \rceil \times 4096 = 112 \times 4096 = 458{,}752 \text{ bytes}$$

With `fifo_size = 524288` (512 KB), there is only $524{,}288 - 458{,}752 = 65{,}536$ bytes (16 pages) of headroom. If the device kernel is slow to pop pages, a second concurrent transfer would exceed the FIFO capacity, and `socket_->write()` would block. If the kernel is also blocked waiting for D2H FIFO space, a deadlock occurs.

**Existing mitigation:** The serialized single-channel design (Section 8.1.4) prevents concurrent H2D writes, so in practice the FIFO only ever holds one transfer. The startup validation catches configuration errors. For future multi-channel designs, the FIFO size must be scaled to `num_concurrent_transfers * padded_payload_size`.

## 8.2.8 Device Launcher Premature Exit: Error Message Lost

**Trigger:** The device launcher binary crashes during initialization (e.g., device not found, tt-metal library version mismatch, HUGEPAGE allocation failure, missing library, permission error accessing `/dev/tenstorrent`).

**Symptom:** The user sees:

```
Device launcher process exited prematurely (status=1)
```

The actual error was printed to the child's stderr but may have scrolled above the parent's error message or been interleaved in log output.

**Root cause:** The `wait_for_descriptors()` method polls both descriptor files and child liveness:

```cpp
// pi05_pipeline_runner.cpp:704-711
if (!is_alive()) {
    int status;
    waitpid(pid_, &status, 0);
    pid_ = -1;
    launched_ = false;
    throw std::runtime_error(
        "Device launcher process exited prematurely (status=" +
        std::to_string(WEXITSTATUS(status)) + ")");
}
```

Three information-loss issues:

1. Since the child inherits the parent's stderr, the error *is* visible in the terminal, but it may be interleaved with the parent's output.
2. `WEXITSTATUS(status)` only gives the exit code (0-255), not the error message.
3. If the child crashed with a signal (SIGSEGV), `WEXITSTATUS` returns 0 and the signal information is in `WTERMSIG(status)`, which is **not checked**.

**Recommended mitigation:** Check `WIFSIGNALED(status)` in addition to `WEXITSTATUS`, and pipe the child's stderr to a log file for post-mortem analysis. The current design relies on the user scrolling up in the terminal or searching the combined log output.

## 8.2.9 D2H Recv Spin-Wait: Warning-Only, No Abort

**Trigger:** The device kernel takes more than 5 seconds to produce a D2H result after the host begins polling.

**Symptom:** The warning message prints to stderr every 5 seconds, but no corrective action is taken:

```cpp
// pi05_pipeline_runner.cpp:579-589
while (!socket_->has_data()) {
    if (++spin_iters % 10000000 == 0) {
        auto elapsed = std::chrono::duration<double>(Clock::now() - spin_start).count();
        if (elapsed > 5.0) {
            std::cerr << "WARNING: D2H recv spin-wait exceeded "
                      << elapsed << "s (" << spin_iters
                      << " iters). Device kernel may be stuck." << std::endl;
            spin_start = Clock::now();
        }
    }
}
```

**Concern:** The spin-wait loop has **no timeout and no abort mechanism**. If the device kernel is truly stuck (e.g., due to a NOC deadlock, an infinite loop, or a hardware fault), the runner spins forever, consuming 100% of one CPU core. There is no timeout, no abort, and no way to recover without externally killing the process.

The spin-wait also generates continuous PCIe polling traffic, which on some systems can interfere with the device kernel's own PCIe transfers.

**Existing mitigation:** The warning serves as a diagnostic signal for operators watching the terminal. The spin-wait is intentional: the framework prioritizes minimum latency for the D2H read (no OS sleep, no futex, no condition variable), which is appropriate for a benchmark measuring microsecond-level transfer times. The `--timeout-s` flag applies only to ALLOCATE and teardown phases, not to D2H spin-waits. A production system would add a configurable timeout that triggers a device reset and reconnect, but this is beyond the scope of a benchmarking framework.
